# Releasing the `@zavudev/sdk` npm package

The SDK is developed in the Zavu monorepo (`sdks/typescript`) and published
from its public mirror,
[zavudev/sdk-typescript](https://github.com/zavudev/sdk-typescript). Every
change to what the package ships goes to npm when it reaches `main`; you only
pick the version.

```
monorepo PR (regenerate, bump the version)
  -> merge into zavudev/zavu main
  -> sync-sdk-typescript.yml pushes the folder to zavudev/sdk-typescript main
  -> its release.yml publishes to npm with provenance, tags v<version>, creates a GitHub Release
```

## The package is generated

`src/` is the output of the SDK generator (`packages/sdk-codegen` in the
monorepo) run on the API's OpenAPI specs: `apps/docs/openapi.json` for v1, and
`apps/docs/api-reference/v2/openapi.json` for `client.v2` (`src/v2/`, mounted
by `mounts` in `zavu.sdk.toml` and laid out by `zavu.v2.sdk.toml`). Never edit
a generated file (they start with `// Generated by zavu-codegen`, or are the
runtime copied from `packages/sdk-codegen/templates/typescript/`): the
monorepo's CI fails when a committed file differs from what the generator
writes, and the next generation undoes the edit anyway.

To change the SDK:

1. Change the spec, the generator config (`packages/sdk-codegen/zavu.sdk.toml`)
   or the runtime templates (`packages/sdk-codegen/templates/typescript/`).
2. Run `packages/sdk-codegen/scripts/codegen.sh generate --target typescript`
   and commit what it writes. A spec change that reaches the SDK must be
   regenerated in the same pull request: the generator's drift test fails
   otherwise.
3. Bump the version (below).

Only `src/lib/` is hand-written; the generator never touches it.
`package.json`, the build configs and scripts, `tests/`, `README.md`,
`CHANGELOG.md` and the other top-level files are hand-maintained.

The package keeps the public surface of `@zavudev/sdk` 0.57.0, the last release
Stainless generated. `packages/sdk-codegen/scripts/test-compat-typescript.sh`
(run by the monorepo's CI) fails when a change breaks a call, a request or a
type name that 0.57.0 had, unless the difference is listed with its reason in
`packages/sdk-codegen/compat/typescript-0.57-expected.txt`.

## Cutting a release

1. In your monorepo pull request, bump the version in two places to the same
   value, then regenerate:

   - `"version"` in `sdks/typescript/package.json`
   - `package_version` under `[targets.typescript]` in
     `packages/sdk-codegen/zavu.sdk.toml`, which the generator writes to
     `VERSION` in `src/version.ts` (`scripts/release.mjs check-version` fails
     when the two differ)

   Add the version's entry to `CHANGELOG.md`.

   We are pre-1.0 (`0.x`), so breaking changes may land in any release. By
   convention: a fix bumps the patch (`0.58.0` → `0.58.1`), anything else the
   minor (`0.58.0` → `0.59.0`). A version with a pre-release part
   (`0.59.0-beta.0`) publishes under the `next` dist-tag; any other version
   becomes `latest`.

2. Merge into `main`. `.github/workflows/sync-sdk-typescript.yml` mirrors
   `sdks/typescript` to `zavudev/sdk-typescript`, where
   `.github/workflows/release.yml` (this folder's `.github/`, at that
   repository's root) lints, tests and builds the package, publishes `dist/`
   with `npm publish --provenance` if npm does not have that version yet, then
   creates the `v<version>` tag and a GitHub Release with generated notes.

Re-running the release is safe: a version npm already has is skipped, and an
existing release is left alone. To run it by hand, open **Actions → Release →
Run workflow** in sdk-typescript on `main`; it is a dry run
(`npm publish --dry-run`) unless you untick `dry-run`. Runs from other
branches can only be dry runs.

Never commit to sdk-typescript directly: the sync stops when that
repository's `main` has commits it did not push (see "When the sync stops").

### What needs a bump

On monorepo pull requests the `Version bumped` check
(`.github/workflows/sdk-version.yml`) fails when any of these changed without
a version above the base branch's:

- `src/**` (becomes `dist/`), `package.json`, `README.md`, `CHANGELOG.md`,
  `LICENSE` (all shipped in the tarball). `src/**` is generated, so a change
  to the OpenAPI spec that changes the SDK lands here too
- `tsconfig.json`, `tsconfig.build.json`, `tsconfig.dist-src.json`,
  `tsc-multi.json`, `scripts/build` and the scripts it runs on `dist/` (they
  decide the build)

Changes to `tests/**`, `packages/**`, `.github/**`, the other `scripts/**`,
`CONTRIBUTING.md`, `SECURITY.md` and this file need no bump; they sync to
sdk-typescript and publish nothing. The rule is `RELEASED` in
`scripts/release.mjs`; the check's message says exactly what to change.

## How the sync works

`sync-sdk-typescript.yml` runs on every push to the monorepo's `main` that
touches `sdks/typescript/**` (and by hand), one run at a time. It runs
`git subtree split --prefix=sdks/typescript` and hands the result to
`scripts/sync-sdk.sh`, which never force-pushes:

- Splits are deterministic: the same history gives the same commits. When
  sdk-typescript's `main` is an ancestor of the new split (merge-commit
  merges, and every normal sync), the split is pushed as a fast-forward and
  the SDK repository gets the monorepo's commits one for one.
- A squash or rebase merge rewrites the monorepo's commits, so the new split
  no longer descends from what was pushed. The script then pushes one join
  commit on top of sdk-typescript's `main`: its tree is exactly the
  monorepo's `sdks/typescript`, its parents are the previous `main` and the
  new split. Still a fast-forward.
- It records what it pushed in the ref `refs/mirror/last-sync` of
  sdk-typescript, in the same atomic push as `main`.

It pushes with an installation token of the `zavu-release-bot` GitHub App,
minted per run and scoped to sdk-typescript with Contents and Workflows write.

### When the sync stops

If sdk-typescript's `main` is not `refs/mirror/last-sync`, someone committed
there directly, and the sync fails with "SDK repository diverged" without
pushing. Port the change to the monorepo and merge it, then mark the SDK
repository's `main` as synced and re-run the workflow:

```sh
git fetch https://github.com/zavudev/sdk-typescript.git main
git push https://github.com/zavudev/sdk-typescript.git FETCH_HEAD:refs/mirror/last-sync
```

The next sync joins `main` to the monorepo's folder with one commit.

## One-time setup

1. **The SDK repository.** `zavudev/sdk-typescript`, public. Its history up
   to 0.57.0 is Stainless's; mark that `main` as synced once (the two
   commands above), and the first sync joins it to the monorepo with one
   commit, keeping the old history.
2. **The sync credentials.** The monorepo's Actions secrets `RELEASE_APP_ID`
   and `RELEASE_APP_PRIVATE_KEY` (the `zavu-release-bot` App, also used by
   `skills-publish.yml`). The App must be installed on sdk-typescript with
   Contents and Workflows read and write: GitHub refuses a push that changes
   `.github/workflows/` without Workflows. The repository must let the push
   through: a "no force pushes or deletion" rule is fine; a rule requiring
   status checks on `main` is not, because CI runs after the sync pushes.
3. **npm trusted publishing (OIDC).** No npm token is needed. On npmjs.com,
   signed in as the account that owns `@zavudev/sdk`, open the package →
   Settings → Trusted publishing and set the GitHub Actions publisher to:

   - Organization or user: `zavudev`
   - Repository: `sdk-typescript`
   - Workflow filename: `release.yml`
   - Environment: leave empty

   `release.yml` has `id-token: write`, runs Node 24 and updates npm to 11.5.1
   or later, which trusted publishing needs. Because sdk-typescript is public,
   npm also records a provenance statement for each version, linking it to the
   commit and the workflow run; that needs `repository.url` in `package.json`
   to be this repository, which it is. Once a release has gone out this way,
   delete the repository secret `NPM_TOKEN` (Stainless's publish workflow used
   it), revoke that token on npm, and set the package's publishing access to
   "Require two-factor authentication and disallow tokens".

`packages/mcp-server` (`@zavudev/sdk-mcp`) is not built or released from
here: Stainless published it, and it stays at 0.57.0.
